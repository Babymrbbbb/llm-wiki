# 01 · raw → wiki → RAG 双轨架构

## 问题：单层 RAG 的局限

直接对原始文档做 RAG，会遇到两个真实问题：

1. **原始资料不可导航**：上千篇散落 markdown，人工检索靠文件名猜，同一主题分散在几十篇里，没人能看完。
2. **泛词塌缩**：垂直领域高频词（会员 / 复购 / 短保…）被大量文档引用，关键词检索被泛词淹没，精确信息排不上来。

## 解法：加一层编译层

```
┌─────────────────────────────────────────────┐
│  raw 层（不可变）                              │
│  L3_原始资料/  （1,641 篇，只读不修改）         │
└────────────────────┬────────────────────────┘
                     │ ingest
                     ▼
┌─────────────────────────────────────────────┐
│  wiki 层（编译产物，可导航）                    │
│  ├── index.md       全局索引（按类型分类）      │
│  ├── log.md         append-only 操作日志      │
│  ├── entity/        品牌/门店/人物/产品实体     │
│  ├── concept/       业务概念/方法论/行业趋势    │
│  ├── comparison/    对比页（A vs B）           │
│  └── synthesis/     跨源综合/策略页             │
└────────────────────┬────────────────────────┘
                     │ 检索
                     ▼
        ┌────────────┴────────────┐
        │ 人工导航（侧边栏文件树）     │
        │ RAG 检索（关键词 + IDF）    │
        └─────────────────────────┘
```

## 为什么双轨而不是单轨

| 方案 | 优点 | 缺点 |
|---|---|---|
| 只做 RAG | 实现快 | 泛词塌缩；不可导航；无法人工校验 |
| 只做 wiki | 可导航 | 静态产物，无法语义召回；更新靠手工 |
| **raw + wiki 双轨** | 保真 + 可导航 + 语义召回 | 多一层编译成本 |

双轨的关键收益：**raw 保真不可变（可回滚、可对账），wiki 可导航聚合（人工与 RAG 共用），任何一层出问题另一层兜底。**

## 落地要点

1. **raw 层只读硬约束**：编译链路绝不修改原始资料，验收时用文件 hash 对账（前后一致）。
2. **wiki 层可推倒重建**：结构升级时整层重建，重建前必须快照可回滚。
3. **编译产物与检索解耦**：AI 分析舱 / RAG / 人工检索都只读 wiki 层，编译与检索互不阻塞。
