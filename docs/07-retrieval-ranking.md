# 07 · RAG 检索排序的演进（v2.1 → v2.4）

> RAG 的「召回」不是查出来就行——**排序质量直接决定 LLM 拿到的上下文对不对**。本仓库的检索器（kb.py 生产版）经过四轮迭代，每一步都是被真实检索问题逼出来的。

## 演进路线

| 版本 | 核心改动 | 解决的真实问题 |
|---|---|---|
| v2.0 | wiki 四类页纳入检索 | 编译产物（entity/concept/comparison/synthesis）检索不到，LLM 编译的知识精华浪费 |
| v2.1 | 准确性加权：标题命中 +60、wiki 层 +40、业务子库 +8、管理文件 −120 | 光快不准没用；日志/待办刷屏，精确信息排不上来 |
| v2.2 | 倒排索引（`search_index.json`）+ 2-gram 候选定位 | 全库扫描太慢；长词/短语无法连续命中 |
| v2.3 | 关联页面推荐（从命中 wiki 页聚合双向链接） | 检索结果孤立，用户/LLM 看不到相关概念（GraphRAG 雏形） |
| v2.4 | 词频饱和（FREQ_CAP=10）+ 业务子库加权 8→25 | 长文件靠重复词刷分；自家一手资料（竞品/产品/门店）优先级不够 |

## v2.4 的两个关键决策

### 1. 词频饱和（`_freq_score`）

```python
FREQ_CAP = 10  # 每个查询词在单篇文档的词频贡献封顶
def _freq_score(count):
    """词频饱和: 超过 FREQ_CAP 后不再线性增加"""
    return min(count, FREQ_CAP)
```

**问题**：一篇 100 页的长文档重复出现「会员」100 次，一篇 1 页的精准文档出现 3 次——按原始词频排序，长文档永远碾压短文档。这不是「相关」，这是「篇幅优势」。

**解法**：单篇词频贡献封顶 10。**长度不再能刷分，相关度回到「命中质量」本身**。这是搜索排序里标准的「词频饱和」（BM25 的 `k1` 参数本质也在做类似的事）。

### 2. 业务子库加权（8 → 25）

**问题**：竞品动态、产品研发、门店管理等**自家一手资料**（实地调研、内部复盘）和行业趋势、公开文章混在一起排序，内部高价值资料经常排不上去。

**解法**：`BUSINESS_SUB_BONUS` 从 8 提到 25。**自家一手资料优先于二手公开资料**——对「内部知识库调取」场景，这个加权方向是决定性的。

## 与 LLM 的关系

这套排序不是孤立存在的——它是 **LLM × RAG 知识库调取系统** 的「召回质量底座」：

```
LLM 编译（离线）           RAG 召回（在线）              LLM 生成（最终）
raw → wiki 四类页   →   v2.4 排序器精确召回   →   检索命中页作为上下文 → 有依据的答案
```

- **LLM 负责「知识组织」**：把散资料编译成结构化 wiki 页，注入 Schema 契约保证行为一致
- **RAG 负责「精确召回」**：v2.4 排序器决定哪些知识页进入 LLM 上下文
- **排序质量 = 答案质量的上限**：喂给 LLM 的上下文错了，模型再强也答不对

## 可复用的方法论

1. **词频必须饱和**：不做饱和，长文档靠篇幅刷分，精准短文档永远吃亏
2. **一手资料要加权**：内部知识库场景，自家数据优先级应高于公开资料
3. **管理文件要重罚**：日志/待办/索引类文件 −120 权重，防止刷屏淹没结论
4. **排序要可解释**：每一条命中都打印相关度分数（标题命中/词频/wiki层/业务子库加权可分解），方便调参
